# Real/Private Operations Transition Specification

## 1. Purpose and Scope

Task 013 defines how this repository can prepare for future real/private business operation while keeping buyer, contact, price, stock, expiry, supplier, final quotation, and private business data out of GitHub.

This specification is a preparation document only. It does not create real data files, private folders, templates, code, workflows, or external communication features.

Task 013 should help the business move from sample/internal-review automation toward a safer operating model by defining:

- Which real/private data categories need protection.
- Which paths should be planned for future ignored storage.
- Which files must never be committed.
- Which manual approval and verification gates are required before any external use.
- Which Privacy Guard improvements are needed before real data migration.
- How sample workflows and future real workflows must remain separated.

The current repository remains sample/internal-review only until a later approved step implements real/private storage, validation, and operating procedures.

## 2. What Task 013 Does Not Do

Task 013 Step A does not:

- Create real data files.
- Create `data/private/`, `output/private/`, or `output/final/` folders.
- Create private templates.
- Modify `.gitignore`.
- Implement code.
- Modify existing automation logic.
- Run real workflows.
- Send emails, DMs, WeChat messages, WhatsApp messages, quotations, or any external communication.
- Implement scraping, live web research, automatic search, APIs, browser automation, crawlers, buyer enrichment, credit checks, or external data collection.
- Verify buyer authenticity, creditworthiness, payment ability, purchase probability, price freshness, stock freshness, expiry validity, or final commercial approval.

Any later real/private workflow requires separate approval, Privacy Guard review, and explicit validation before use.

## 3. Planned but Not-Created Real/Private Folder Structure

The following folder structure is recommended for future design only. Step A must not create these folders.

```text
data/private/
  buyers/
  contacts/
  pricing/
  stock/
  expiry/
  quotations/
  supplier_terms/
  approvals/
  localization/

output/private/
  proposals/
  quotations/
  reports/
  dashboards/

output/final/
  proposals/
  quotations/
  contracts/

local_config/
```

Planned folder rules:

- `data/private/**` should store future real input data only after it is confirmed ignored.
- `output/private/**` should store generated real-data internal-review outputs only after it is confirmed ignored.
- `output/final/**` should remain outside the current automation scope and must not be generated by existing scripts.
- `local_config/**` should be used only for local non-committed configuration if a future approved workflow needs it.
- No private folder should be created until `.gitignore` protection, Privacy Guard checks, and manual operating rules are reviewed.

## 4. Real/Private Input Categories

Future real/private operation may involve these data categories:

| Category | Examples | GitHub status | Required handling |
| --- | --- | --- | --- |
| Buyer identity | Real buyer company names, contact persons, buyer notes | Must not be committed if sensitive | Store in ignored/private storage only |
| Contact data | `contact_email`, `contact_phone`, `wechat_id`, `whatsapp`, SNS handles tied to real people | Must not be committed | Mask or keep in ignored/private storage |
| Price data | Supplier price lists, price validity dates, currency, discounts | Must not be committed | Verify manually before use |
| Stock data | Stock list, inventory, available quantity, supply availability | Must not be committed | Verify manually before quote |
| Expiry data | Expiry dates, lot/batch notes, shelf-life constraints | Must not be committed | Recheck before quote |
| Quotation inputs | Real requested quantity, unit price, MOQ, delivery terms, buyer-specific conditions | Must not be committed | Internal review only |
| Quotation outputs | Draft real quotations, buyer-specific quotation summaries | Must not be committed | Internal review; final output outside current scope |
| Supplier terms | Payment terms, contract terms, incoterms, shipping terms, duties, taxes | Must not be committed | Manual commercial/legal review |
| Approval records | Director approval, brand-specific permissions, proposal eligibility exceptions | Usually must not be committed | Store in secure approval record system |
| Localization | Private translated buyer messages, China channel notes, local compliance notes | Must be reviewed | Keep private if buyer-specific or confidential |

## 5. Files That Must Never Be Committed

The following must not be committed to GitHub:

- Real buyer/contact data.
- `contact_email`, `contact_phone`, `wechat_id`, `whatsapp` values for real buyers.
- Real buyer notes containing personal or private business context.
- Real price lists.
- Real stock lists.
- Real expiry lists.
- Real supply availability files.
- Real quotation input files.
- Real quotation output files.
- Final quotation files.
- Supplier terms.
- Payment terms.
- Contract terms.
- Incoterms.
- Tax, shipping, duties, customs, or insurance files containing real commercial terms.
- Confidential approval records.
- Credentials, tokens, `.env`, keys, local settings, or private config.
- Any file named like `*_real.csv`, `*_private.csv`, `*_contacts.csv`, `*_prices.csv`, `*_stock.csv`, `*_expiry.csv`, `*_quotation_final.*`, `*_supplier_terms.*`, `*_payment_terms.*`, or `*_incoterms.*` unless it is safely ignored and not staged.

If a file might contain real/private business data, treat it as sensitive until manually cleared.

## 6. Sample Workflow vs Real Workflow Separation

Current sample workflows:

- Use fictional/sample data only.
- Use tracked or sample-safe files under `data/`.
- Generate internal-review outputs under `output/`, most of which are ignored.
- Do not use `data/private/**`, `output/private/**`, or `output/final/**`.
- Do not send external messages or quotations.

Future real workflows must:

- Use separate ignored/private paths only.
- Never overwrite tracked sample CSV files with real business data.
- Preserve source sample workflows so validators and examples remain safe.
- Run Privacy Guard before and after any real-data preparation step.
- Keep all outputs internal-review only unless a later approved human workflow creates final external documents outside the current automation scope.
- Never treat an internal `PASS` result as permission for external use.

Recommended naming distinction:

- Sample: `*_sample.csv`, `sample_*`, `output/*_sample.*`
- Real/private: `*_real.csv`, `*_private.csv`, private folder paths, or secure storage outside the repository

## 7. Privacy Guard Strengthening Requirements

Before real/private operation is introduced, Privacy Guard should be reviewed and strengthened to check:

- Any real/private path accidentally staged.
- Any sensitive filename pattern staged.
- Real-looking emails outside approved placeholder domains.
- Real-looking phone numbers in sample files.
- Real WeChat or WhatsApp identifiers in sample or public outputs.
- Contact field names or values in generated public/internal summaries where they should be excluded.
- Real price, stock, expiry, quotation, supplier term, payment term, contract term, and incoterm filenames.
- Final quotation or external-ready wording in generated outputs.
- Missing internal-review disclaimers in proposal, quotation, dashboard, and report outputs.
- Approval-required brand misuse, especially `메디큐브`/Medicube.
- Attempts to use `data/private/**`, `output/private/**`, `output/final/**`, or `local_config/**` in sample workflow commands.
- Any new code importing or using external collection, enrichment, credit check, browser automation, or external sending patterns.

Privacy Guard should block unsafe validation, report clear failures, and require manual review. It must not delete, move, rewrite, stage, commit, or push files automatically.

## 8. Manual Approval Gates Before External Use

No generated output should be used externally until all relevant manual gates pass.

Required gates:

1. Privacy review: confirm no private buyer/contact/commercial data is exposed.
2. Buyer review: confirm buyer identity, contact permission, and communication appropriateness manually.
3. MOQ review: confirm the buyer can meet the generally required 100+ units or has a reviewed exception.
4. Brand approval review: confirm approval-required brands are cleared before proposal, quotation, public content, or buyer-facing copy.
5. Product and claim review: confirm cosmetics claims, before/after references, medical-like language, and functional claims are allowed and supported.
6. Commercial review: confirm price, stock, expiry, MOQ, delivery, tax, shipping, duties, payment terms, and incoterms.
7. Localization review: confirm Korean, English, Chinese, or local-language wording is appropriate.
8. Final human approval: confirm the final external document or message is approved outside the automation workflow.

Automation output is a draft or internal planning artifact until these gates are completed.

## 9. Medicube and Approval-Required Brand Handling With Real Data

`메디큐브`/Medicube remains approval-required unless explicit approval is recorded by the responsible director or approved business process.

Real-data rules:

- Buyer interest in `메디큐브`/Medicube may be recorded privately as buyer interest.
- `메디큐브`/Medicube must not be automatically recommended in external proposal, buyer-facing pitch, public content, ad copy, or quotation output without explicit approval.
- `approval_block=true` must override `priority_tier`, `score_total`, buyer interest, and expected order quantity.
- A high buyer score, A-tier priority, or large order quantity must not override brand approval restrictions.
- Approval records may be confidential and should not be committed if they include private approval context.
- Brands with `approval_required=true` or `proposal_allowed=false` must be treated as review-required or blocked until explicit approval is recorded.

The system must keep opportunity priority separate from approval readiness.

## 10. Commercial Verification Rules

Before any real external proposal or quotation, the following must be manually verified:

- Price and currency.
- Price validity date.
- Stock status and available quantity.
- Expiry date and shelf-life suitability.
- MOQ and any exception to MOQ.
- Delivery lead time.
- Supply availability.
- Payment terms.
- Shipping terms.
- Tax.
- Duties.
- Customs requirements.
- Insurance, discounts, and other commercial adjustments.
- Incoterms.
- Supplier-specific restrictions.

Generated totals must be treated as draft calculations only. Unless manually verified, totals should exclude tax, shipping, duties, customs fees, insurance, discounts, payment terms, and incoterms.

Missing or stale commercial data must trigger confirmation-needed status, not final quotation readiness.

## 11. Final Quotation Restrictions

The current automation foundation generates internal-review quotation drafts only.

Rules:

- No script should create a final external quotation in the current scope.
- No script should send quotations externally.
- `output/final/**` must not be used until a future approved final-document process exists.
- Final quotations require human review, brand approval, commercial verification, and buyer-specific approval.
- Quotation validation `PASS` means format/safety validation passed; it does not mean final commercial approval.
- A quotation draft with `approval_block=true`, missing price, missing stock, missing expiry, MOQ issue, or missing terms must remain internal-only.
- Final quotation storage should be outside GitHub or in an approved secure system.

## 12. External Communication Restrictions

This repository must not send external communication.

Not supported:

- Email sending.
- DM sending.
- WeChat sending.
- WhatsApp sending.
- Platform posting.
- Quotation sending.
- External proposal sending.
- Buyer outreach automation.
- External message scheduling.

Proposal messages, quotation drafts, reports, dashboards, scoring outputs, and content plans are internal-review outputs only. Actual external communication must be manual and separately approved.

## 15. Remaining Risks

Remaining risks:

- Privacy Guard is not a full data loss prevention system.
- Human review is still required before commit and before external use.
- Real data may be placed in the wrong path if operators do not follow policy.
- Ignored/private paths protect Git commits but do not solve local machine security.
- GitHub repository visibility and access control must be reviewed before real data work.
- Real buyer contact handling may require consent, masking, or stricter access controls.
- Commercial data can become stale quickly.
- Approval-required brand misuse remains a business-critical risk.
- `score_total` can be misunderstood as buyer reliability or purchase probability.
- Dashboard or runner `PASS` can be misunderstood as external approval.
- Quotation validation `PASS` can be misunderstood as final commercial approval.
- Future XLSX/CSV/private outputs require separate validation design.
- External communication remains manual and must not be automated by this repository without separate approval.
